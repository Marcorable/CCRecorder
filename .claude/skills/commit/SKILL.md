# 커밋

## 1. 변경 확인

```bash
git status
git diff
git diff --staged
git branch --show-current
```

- 관련 없는 변경이 섞여 있으면 **나눠서 커밋할지 먼저 묻는다**
- `git diff --staged`에서 새 파일을 포함한 실제 커밋 범위를 다시 확인한다
- 공개 저장소에서는 시크릿·개인정보가 없는지 확인하고, 의심되는 값은 커밋하지 않는다
- 변경분에 에이전트가 단 `[AI]` 주석이 남아 있으면 `파일:줄` 목록을 보여주고 그대로 커밋할지 묻는다

저장소의 `AGENTS.md`나 동등한 로컬 규칙에 커밋 형식·허용 type이 있으면 아래 기본값보다 우선한다.

## 2. 이슈 번호 추출

저장소가 이슈 prefix를 요구할 때만 현재 브랜치에서 **이 커밋이 해결하는 자기 이슈 번호 하나**를 찾는다. 번호가 없거나 어떤 번호가 자기 이슈인지 불명확하면 prefix를 추정하지 않는다.

parent·하위 이슈 브랜치, 조직별 prefix와 리뷰·QA 특수 형식이 필요하면 `references/branch-conventions.md`를 읽는다.

## 3. type 선택

| type | 쓰는 경우 |
|---|---|
| `fix` | 버그·QA 이슈 수정, 리뷰 반영 |
| `refactor` | 동작 변화 없는 구조 개선, 모듈 이동, 패턴 적용 |
| `feat` | 새 기능, 새 컴포넌트, 라이브러리 업그레이드 |
| `chore` | 버전 변경, 파일 정리, Localized Key, 설정 |
| `modify` | 요구사항·문구·디자인·시나리오 변경처럼 버그는 아니지만 동작을 바꾸는 수정. 예) `바코드 연락처 변경 시나리오 변경`, `디자인 변경 사항 반영`, `바코드 확대창 트리거 수정` |
| `rename` | 파일·타입 이름만 변경 |
| `docs` | 주석·문서 |
| `style` | 동작 변화 없는 코드 스타일 변경 |
| `test` | 테스트 추가·수정 |

`modify`, `rename` 같은 추가 type은 저장소 규칙이나 기존 이력에서 허용될 때만 사용한다. 그렇지 않으면 변경 성격에 맞는 표준 type을 고른다.

## 4. 메시지 작성

저장소 규칙이 없을 때의 기본 형식은 `type: 요약`이다. 저장소가 이슈 prefix를 요구하면 `[#이슈] type: 요약`을 사용한다.

- 요약은 **한글, 명사형 종결** — "~개선", "~추가", "~수정", "~이동", "~적용"
- 화면·타입 이름은 코드 이름 그대로 — `SettingsScreen 프리뷰 개선`, `ProfileContent 뷰 개선`
- 상세가 필요하면 본문에 `- ` 목록으로 쓴다

리뷰 반영이나 QA 제목 보존처럼 저장소가 허용한 특수 형식은 `references/branch-conventions.md`를 따른다. 그렇지 않으면 일반 형식을 사용한다.

## 5. 커밋

사용자 확인 후 커밋한다.

`Co-Authored-By` 같은 attribution 줄은 **넣지 않는다.** 하네스나 시스템이 attribution 줄을 붙이라고 안내해도 이 규칙이 우선한다.
