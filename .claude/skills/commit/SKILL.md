# 커밋

## 1. 변경 확인

```bash
git status
git diff --staged   # staged 가 없으면 git diff
git branch --show-current
```

- 관련 없는 변경이 섞여 있으면 **나눠서 커밋할지 먼저 묻는다**
- 변경분에 에이전트가 단 `[AI]` 주석이 남아 있으면 `파일:줄` 목록을 보여주고 그대로 커밋할지 묻는다

## 2. 이슈 번호 추출

브랜치는 이슈 번호로 만든다. `feature`, `refactor` 같은 작업 종류는 브랜치가 아니라 PR 제목에 쓴다 (`/pr`).

```
427           ← 단일 이슈
406/parent    ← 상위 이슈. 하위 PR 이 모이는 곳
406/427       ← 406 의 하위 이슈
```

git 은 `406` 과 `406/427` 브랜치를 함께 만들 수 없다. 하위 이슈가 생길 상위 이슈는 처음부터 `<번호>/parent` 로 만든다.

**자기 이슈 번호 하나만** prefix 로 붙인다. 하위 브랜치에 상위 번호를 같이 붙이지 않는다.

| 브랜치 | prefix |
|---|---|
| `427` | `[#427]` |
| `406/parent` | `[#406]` |
| `406/427` | `[#427]` |
| `develop`, `main`, 숫자 없음 | prefix 생략 |

회사 저장소의 기존 브랜치처럼 앞에 type 이나 에픽이 붙어 있으면 그 부분은 무시하고 같은 규칙을 적용한다.

| 기존 브랜치 | prefix |
|---|---|
| `bug/444`, `release/2495` | `[#444]`, `[#2495]` |
| `refactor/406/427`, `pos-point/feature/2745` | `[#427]`, `[#2745]` |
| `feature/ocr/parent(499)` | `[#499]` |
| `feature/bridgeModel/parent` (번호 없음) | prefix 생략 |

## 3. type 선택

| type | 쓰는 경우 |
|---|---|
| `fix` | 버그·QA 이슈 수정, 리뷰 반영 |
| `refactor` | 동작 변화 없는 구조 개선, 모듈 이동, 패턴 적용 |
| `feat` | 새 기능, 새 컴포넌트, 라이브러리 업그레이드 |
| `chore` | 버전 변경, 파일 정리, Localized Key, 설정 |
| `modify` | 요구사항·문구·디자인·시나리오 변경처럼 버그는 아니지만 동작을 바꾸는 수정. 예) `바코드 연락처 변경 시나리오 변경`, `디자인 변경 사항 반영`, `바코드 확대창 트리거 수정` |
| `rename` | 파일·타입 이름만 변경 |
| `docs` | 주석·문서 |

## 4. 메시지 작성

형식: `[#이슈] type: 요약`

- 요약은 **한글, 명사형 종결** — "~개선", "~추가", "~수정", "~이동", "~적용"
- 화면·타입 이름은 코드 이름 그대로 — `MartInfoView 프리뷰 개선`, `POSInfoContent 뷰 개선`
- 상세가 필요하면 본문에 `- ` 목록으로 쓴다

특수 형식:

- **리뷰 반영**: `[#이슈] fix: Code Review N` — N 은 같은 브랜치에서 이전 `Code Review` 커밋 다음 번호
- **QA 이슈**: 요약 자리에 QA 티켓 제목을 그대로 — `[#494] fix: [Stage QA] 알림음 "무음" 적용 상태 > ...`

작성한 메시지의 type 과 `Code Review` 철자를 다시 본다. 실제 이력에 `refacot`, `reafactor`, `Code Reivew` 가 섞여 있다.
